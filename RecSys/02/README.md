# 🎵 ДЗ #02: Botify — Рекомендательная система музыкальных треков

## 💡 Основная идея

Необходимо предложить улучшение рекомендательного сервиса **Botify** и подтвердить его эффективность с помощью A/B-эксперимента.

**Критерий успеха** — статистически значимое улучшение метрики `mean_session_time` по сравнению с **User-Based recommender**.

Для проверки необходимо провести честный A/B-тест:

- **Контрольная группа (C)** — User-Based recommender.
- **Тестовая группа (T1)** — разработанный рекомендательный алгоритм.

## 📋 Подробное описание

### 🔹 Исходные рекомендательные алгоритмы

В Botify представлены четыре рекомендательных подхода:

- **StickyArtist** — рекомендации на основе исполнителя.
- **User-Based** — коллаборативная фильтрация по пользователям.
- **LightFM Item-to-Item** — рекомендации похожих треков.
- **SasRec Item-to-Item** — рекомендации на основе последовательностей взаимодействий.

В исходном эксперименте используются следующие группы:

| Группа | Рекомендатель |
|---|---|
| C | StickyArtist |
| T1 | User-Based |
| T2 | LightFM Item-to-Item |
| T3 | SasRec Item-to-Item |

### 🔹 Разработка улучшения

Необходимо:

1. Подготовить данные для обучения рекомендательной модели.
2. Разработать и обучить ML-алгоритм рекомендаций.
3. Интегрировать разработанный алгоритм в сервис Botify.
4. Настроить A/B-эксперимент с User-Based в контрольной группе.
5. Провести эксперимент и проверить статистическую значимость улучшения метрики `mean_session_time`.

### 🔹 Разрешено

- Использовать любые алгоритмы машинного обучения, в том числе не рассмотренные в рамках курса.
- Совместно собирать и использовать данные симулятора с другими студентами.

### 🔹 Запрещено

- Копировать решения других студентов. За неуникальность предусмотрен штраф.
- Использовать для обучения внутренние данные модуля `sim`.
- Отправлять в качестве решения эвристические модификации SasRec-I2I. Улучшение должно быть получено с помощью ML.

## 🧪 Формат проверки

### 1. Проверка A/B-эксперимента

- Контрольная группа должна использовать **User-Based recommender**.
- Тестовая группа должна использовать разработанный рекомендатель.
- Основная метрика — `mean_session_time`.
- Требуется статистически значимое улучшение относительно контроля.

### 2. Проверка отчёта

В корне репозитория должен находиться файл `report.md` объёмом **не более одной страницы**, содержащий:

- **Abstract** — основная идея эксперимента (1 абзац).
- **Детали реализации** — краткое описание подхода (1–2 абзаца и диаграмма).
- **Результаты A/B-теста** — описание и таблица результатов.
- **Инструкция по запуску** — достаточная для воспроизведения решения на другом компьютере.

### 3. Проверка кода

Проверяющий изучает реализацию, корректность интеграции алгоритма и выполнение ограничений задания.

При подозрении на неуникальность решения может быть назначен штраф.

## 📦 Условия сдачи

- Реализация рекомендательного алгоритма.
- Отчёт `report.md` в корне репозитория.
- **Merge Request из личного форка в основной репозиторий курса.**
- Временем сдачи считается время последнего коммита в MR.
- После проверки преподаватель оставляет комментарий с результатом.
- При согласии с оценкой MR необходимо **закрыть, не выполняя Merge**.

## ⚠️ Штрафы и критерии оценки

Максимальная оценка — **35 баллов**.

Оценка может быть снижена за:

- Отсутствие улучшения относительно контрольного рекомендателя.
- Невалидный эксперимент (неправильная контрольная группа).
- Сходство с ранее представленными решениями.
- Просрочку сдачи.

Формула итоговой оценки:

\[
35 \times 0.95^{(1+d)} \times 0.95^k
\]

где:

- `d` — количество полных суток после дедлайна; если работа сдана вовремя, `d = −1`.
- `k` — количество аналогичных решений, встреченных проверяющему до проверки данной работы.
