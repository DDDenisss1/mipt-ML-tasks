## 💡 Архитектура решения

Разработан рекомендательный алгоритм **Implicit ALS (Alternating Least Squares)**, использующий неявную обратную связь пользователей музыкального сервиса Botify.

Цель — повысить среднюю продолжительность пользовательской сессии относительно **User-Based Collaborative Filtering** и подтвердить улучшение статистически значимым A/B-экспериментом.

Для обучения использовались логи прослушиваний, собранные через симулятор пользовательского поведения и API Botify. На их основе строилась разреженная матрица взаимодействий пользователей с треками, обучалась ALS и формировались персонализированные списки рекомендаций.

**Архитектура:**

```text
                 Music Simulator
                        │
                        ▼
                 Botify API (Flask)
                        │
                        ▼
                 Interaction Logs
                        │
                        ▼
                 Preprocessing
                        │
                        ▼
                 User-Item Matrix
                        │
              ┌─────────┴─────────┐
              ▼                   ▼
         User-Based          Implicit ALS
              │                   │
              ▼                   ▼
       Recommendations      Top-100 Tracks
              │                   │
              └─────────┬─────────┘
                        ▼
                  Redis Storage
                        │
                        ▼
                 A/B Experiment
              C: User-Based / T1: ALS
                        │
                        ▼
               Statistical Analysis
```

Рекомендации предварительно рассчитываются и сохраняются в Redis. Это позволяет интегрировать обученную модель в существующий сервис без реализации отдельного онлайн-инференса.

## 🔹 2. Подготовка данных для Implicit ALS

### Неявная обратная связь

В музыкальном сервисе отсутствуют явные оценки треков, поэтому вместо рейтингов применяется **implicit feedback** — продолжительность пользовательских прослушиваний.

Для каждого взаимодействия рассчитывается положительный сигнал:

```python
weight = max(0, listen_time - 0.2)
```

Значение `0.2` используется как порог для подавления очень коротких взаимодействий.

Повторные взаимодействия одного пользователя с одним треком агрегируются. Полученные значения формируют веса в матрице пользователь–трек.

### Разреженная матрица взаимодействий

Матрица имеет размерность:

\[
R \in \mathbb{R}^{N_{users} \times N_{items}}
\]

Каждая строка соответствует пользователю, каждый столбец — музыкальному треку.

**Почему разреженная матрица?** Пользователи прослушивают только небольшую часть каталога. Хранение отсутствующих взаимодействий в плотной матрице привело бы к избыточному расходу оперативной памяти.

### Confidence weighting

Для обучения используется взвешивание уверенности в пользовательских предпочтениях:

\[
c_{ui} = 1 + \alpha r_{ui}
\]

где:

- \(r_{ui}\) — агрегированный положительный сигнал взаимодействия.
- \(\alpha = 40\) — коэффициент усиления уверенности.

Чем продолжительнее прослушивания, тем выше уверенность модели в соответствующем пользовательском предпочтении.

## 🔹 3. Обучение модели ALS

### `train_als.py`

Implicit ALS выполняет матричную факторизацию, обучая скрытые представления пользователей и треков.

Основная идея:

\[
R \approx UV^T
\]

где \(U\) — матрица пользовательских факторов, \(V\) — матрица факторов треков.

Оценка релевантности трека для пользователя:

\[
\hat r_{ui} = U_u \cdot V_i
\]

ALS попеременно оптимизирует пользовательские и трековые факторы, минимизируя взвешенную ошибку с регуляризацией.

### Гиперпараметры

| Параметр | Значение |
|---|---:|
| Количество факторов | 64 |
| Регуляризация | 0.1 |
| Количество итераций | 30 |
| Confidence alpha | 40 |
| Random seed | 42 |
| Количество рекомендаций | 100 |

### Генерация Top-100

После обучения выполняются следующие действия:

1. Для пользователя рассчитываются оценки треков через скрытые факторы.
2. Ранее прослушанные треки исключаются из кандидатов.
3. Остальные треки ранжируются по предсказанному предпочтению.
4. Формируется персонализированный Top-100.
5. Результаты сохраняются в JSON для загрузки в Redis.

**Почему офлайн-генерация рекомендаций?** Исходный Botify уже поддерживает рекомендатели, выдающие треки из заранее подготовленных списков. Такой подход позволил использовать существующую архитектуру и избежать дополнительных вычислений матричной факторизации при каждом API-запросе.

## 🔹 4. Контрольная модель User-Based

### `train_user_based.py`

Для сравнения реализована модель **User-Based Collaborative Filtering**, использующая историю взаимодействий пользователей.

Основная идея — определить пользователей со схожими музыкальными предпочтениями и рекомендовать треки на основе их взаимодействий.

В отличие от ALS, которая обучает компактные латентные представления, User-Based непосредственно использует сходство пользовательских историй.

**Почему контроль обучался самостоятельно?**

В исходном учебном репозитории не было готового файла персональных рекомендаций User-Based. Поэтому контрольная модель была подготовлена на тех же обучающих логах, что и ALS.

Это позволило выполнить A/B-сравнение двух подходов при общем источнике обучающих данных.

При этом собственная реализация User-Based не обязательно полностью совпадает с реализацией из семинарского Jupyter Notebook.

## 🔹 5. Интеграция модели в Botify

### `server.py`

Новая модель интегрирована в существующий API Botify через хранилище Redis и класс `Indexed`.

Использовалось разделение логических баз Redis:

| Redis DB | Содержимое |
|---|---|
| 3 | User-Based |
| 4 | LightFM Item-to-Item |
| 5 | SasRec Item-to-Item |
| 6 | Implicit ALS |

Для ALS добавлена конфигурация загрузки рекомендаций из `recommendations_als.json`.

При запуске сервиса готовые рекомендации загружаются в Redis, после чего становятся доступны через тот же HTTP API, который использовался исходными алгоритмами.

### Выбор модели

Ключевой фрагмент логики `server.py`:

```python
treatment = Experiments.HOMEWORK.assign(user)

if BOOTSTRAP:
    recommender = sticky_artist_recommender
elif treatment == Treatment.C:
    recommender = ub_recommender
elif treatment == Treatment.T1:
    recommender = als_recommender
```

В полной реализации сохранены остальные предусмотренные исходным сервисом варианты выбора рекомендателей.

**Ключевое решение:** интеграция ALS не требует менять клиентские запросы или разрабатывать новый API. Пользователь обращается к прежнему endpoint, а сервер выбирает рекомендательный алгоритм по назначенной группе эксперимента.

## 🔹 6. Настройка A/B-эксперимента

### `experiment.py`

Для основного теста используется эксперимент `HOMEWORK`:

```python
HOMEWORK = Experiment("HOMEWORK", Split.HALF_HALF)
```

Назначение группы определяется через MurmurHash3 на основе идентификатора пользователя и названия эксперимента.

Это обеспечивает **детерминированное распределение**: один пользователь при повторных запросах остаётся в той же экспериментальной группе.

### Основной эксперимент

| Группа | Алгоритм |
|---|---|
| C — контроль | User-Based |

Распределение проверено на 10 000 идентификаторов пользователей:

| Группа | Количество | Доля |
|---|---:|---:|
| C | 4 927 | 49.27% |
| T1 | 5 073 | 50.73% |

Распределение близко к ожидаемому 50/50.

### Дополнительное сравнение

Отдельно был проведён эксперимент ALS против SasRec Item-to-Item.

Для него временно использовалась конфигурация:

- C — SasRec Item-to-Item.
- T1 — Implicit ALS.

После дополнительного сравнения восстановлена итоговая конфигурация **User-Based vs ALS**, соответствующая условию задания.

## 🔹 7. Статистический анализ A/B-тестов

### `analyze_ab.py`

Анализатор обрабатывает журналы взаимодействий Botify и восстанавливает пользовательские сессии.

Сессия завершается событием `last`.

Для каждого пользователя формируются агрегированные метрики:

| Метрика | Значение |
|---|---|
| `time` | Суммарное время прослушивания |
| `sessions` | Количество завершённых сессий |
| `mean_request_latency` | Средняя задержка запроса |
| `mean_tracks_per_session` | Среднее число треков за сессию |
| `mean_time_per_session` | Среднее время прослушивания за сессию |

Основная метрика проекта:

\[
\text{mean\_time\_per\_session}
=
\frac{\text{total listening time}}{\text{number of sessions}}
\]

### Расчёт относительного эффекта

\[
\text{Effect} =
\frac{\overline{X}_{T1}-\overline{X}_{C}}
{\overline{X}_{C}} \times 100\%
\]

Сначала рассчитываются пользовательские метрики, затем выполняется сравнение средних значений групп.

Такой подход учитывает, что несколько прослушиваний одного пользователя не являются независимыми наблюдениями.

### Проверка статистической значимости

Для оценки неопределённости применяется **95%-й доверительный интервал разности средних с поправкой Уэлча**.

Используются:

- Средние значения контрольной и тестовой групп.
- Выборочные дисперсии.
- Число пользователей в каждой группе.
- Критические значения распределения Стьюдента через `scipy.stats.t.ppf`.

Результат признаётся статистически значимым, если доверительный интервал разности средних не содержит ноль.

### Исправление выбора эксперимента

Исходный анализатор выбирал первый эксперимент в алфавитном порядке. Поскольку в логах одновременно присутствовали `AA` и `HOMEWORK`, анализ мог выполняться не по тому эксперименту.

Добавлена явная проверка:

```python
if "HOMEWORK" not in keys:
    raise ValueError("Эксперимент HOMEWORK отсутствует в логах")
exp = "HOMEWORK"
```

Это исключило случайный выбор `AA` вместо основного A/B-эксперимента.

## 🔧 Возможные улучшения для production

1. **Cold Start.** Разработать отдельную стратегию для новых пользователей и треков, отсутствующих в обучающей выборке.
2. **Регулярное переобучение.** Автоматизировать подготовку логов, обновление ALS и публикацию рекомендаций.
3. **Онлайн-инференс.** Перейти от полностью предрассчитанных списков к более оперативному учёту новых взаимодействий.
4. **Подбор гиперпараметров.** Оптимизировать число факторов, регуляризацию, коэффициент confidence и размер Top-N.
5. **Офлайн-оценка.** Добавить Recall@K, NDCG@K, coverage и diversity.
6. **Мониторинг A/B.** Добавить SRM-проверки, контроль технических ошибок и автоматическое формирование статистических отчётов.
7. **Качество данных.** Проверять полноту событий, дубликаты, корректность границ сессий и стабильность распределения групп.
